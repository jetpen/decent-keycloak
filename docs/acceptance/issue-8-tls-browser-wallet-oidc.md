## Qualification decisions

- **Native wallet client and ownership:** Keycloak #8 will qualify the Android app specified by [Wallet #66](https://github.com/jetpen/decent-wallet/issues/66), using its `apps/android-wallet-client` module. Wallet owns its approval UI, verified App Link entry point, native challenge GET, exact-proof POST, and app-level acceptance gates. Keycloak #8 consumes a Wallet-approved revision only after those Wallet-owned gates pass; the signer-only Wallet #64 change and Wallet fixture tests are not Issue #8 qualification.
- **Public origin and TLS:** Use `https://ben-x260.tailca8b51.ts.net` as the provider/App Link host, exposed through Tailscale Funnel only during the disposable qualification run. Route it only to the disposable Keycloak instance. The positive flow uses Funnel's automatically provisioned publicly trusted HTTPS certificate and ordinary Chromium/Android certificate-chain and hostname validation. Serve the Android App Link association at `/.well-known/assetlinks.json` on that publicly reachable HTTPS host without redirects, as required by [Android App Links guidance](https://developer.android.com/training/app-links/configure-assetlinks). The Funnel-facing route must serve this file separately from provider paths forwarded to Keycloak; verify the response contains the exact package name and signing-certificate fingerprint from the Wallet-approved app revision. The dedicated test CA is reserved for explicit TLS-negative cases: the negative-test browser/device profiles must not trust that CA, and must reject its certificate even when its SAN matches the selected host. Test hostname mismatch separately with a normally trusted certificate. A TLS rejection in the Android app must result in no proof POST. Never use trust-all TLS or weaken hostname checks.
- **Android target:** Use a disposable configured Android emulator running the Wallet #66 app. Record the exact Android image/API and app revision in the sanitized receipt; do not treat the emulator fixture run as the separate Keycloak/Chromium/Android qualification.
- **Public exposure constraint:** Tailscale documents Funnel as the public exposure path for a tailnet service and automatically provisions its HTTPS certificate ([Funnel documentation](https://tailscale.com/docs/features/tailscale-funnel)). Keep Funnel disabled outside the controlled run window.

These decisions select the qualification path; they do not qualify any gate or authorize production use. Issue #8 remains open until the full positive and negative real-client matrix and its sanitized receipt are verified.

## Implementation and verification record

The offline OIDC-validation slice is intentionally narrower than the full issue. Its pinned runtime is in [`requirements/issue8-oidc.lock`](../../requirements/issue8-oidc.lock). The live harness now:

- pins `RS256` and requires exactly one matching RSA signing key from the realm JWKS;
- verifies the JWT signature through `joserfc` using the JWKS key set; and
- validates expected `iss`, `aud`, `nonce`, and registered ID-token claims using Authlib `CodeIDToken`.
