**Checked:** 2026-11-01

## Findings and gate status

### GHCR suitability and permissions — technical suitability and metadata-read access verified; write remains unavailable

GHCR is technically suitable as a candidate registry: GitHub Container Registry supports Docker v2 schema 2 and OCI image formats, and public container packages can be pulled anonymously. A package may inherit the linked repository's access or have granular package permissions; a linked repository's Actions workflow can be granted package access. GitHub's documented token scopes are `read:packages` for pulling, `write:packages` for pushing, and `delete:packages` for deletion. For Actions, GitHub recommends `GITHUB_TOKEN`; publishing requires `packages: write` and package access. These facts establish a viable mechanism, **not** this project's authorization or package policy. [Container registry docs](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry); [package permissions](https://docs.github.com/en/packages/learn-github-packages/about-permissions-for-github-packages); [Actions workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

After the user refreshed the active `gh` credential, `gh auth status` reported `read:packages` and no `write:packages` or `delete:packages`. Authenticated requests to `user/packages?package_type=container&per_page=100` and `users/jetpen/packages?package_type=container&per_page=100` both succeeded; the visible `jetpen` user namespace contained **zero container packages**. This verifies metadata-list access and that no visible GHCR container package currently exists in the namespace. There is therefore no package whose visibility, linked-repository/inherited permissions, package-specific read/write access, or retention settings can be inspected. The prior anonymous GHCR token request for `jetpen/decent-keycloak` returned HTTP 403; that 403 was not itself evidence of absence. The current PR workflow grants `contents: read` and has no registry login, push, or package-write grant (`.github/workflows/acceptance.yml`). [Existing lifecycle evidence](issue-26-image-lifecycle.md#remote-registry-and-expiry-status); [workflow](../../.github/workflows/acceptance.yml).

**Can close:** GHCR technical suitability, the required permission model, successful `read:packages` metadata access, and the package-absence result for the `jetpen` user namespace are verified. **Still unavailable:** package-specific read/write/delete settings and actual write authorization because no package exists and the credential lacks write/delete scopes. The accepted safe alternative is to keep PR CI and local workflows non-publishing and consume local images by immutable ID; do not enable a GHCR publisher or claim a remote image exists. Any later GHCR publication requires a deliberate package configuration, authorized write access, and digest read-back.

### Remote expiry, release, and maximum retention — manual control exists; registry-enforced TTL not established

GitHub's Container Registry docs describe package publishing, access, tags, and image operations, but do not document an age-based package TTL or automatic version-retention policy. GitHub does provide package/version deletion via UI and REST API. Deleting a package version requires `read:packages` + `delete:packages` and the appropriate package admin access; GitHub Actions deletion/restoration via REST is documented as public preview and requires package `admin` permission. Deleted packages/versions are restorable only within 30 days and only if the namespace/version remains available. A public package version with more than 5,000 downloads cannot be deleted through the documented normal deletion path; GitHub directs owners to Support. Deleting a public version may break consumers. [Delete/restore guidance](https://docs.github.com/en/packages/learn-github-packages/deleting-and-restoring-a-package); [REST package endpoints](https://docs.github.com/en/rest/packages/packages); [Container registry docs](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

Thus a scheduled, maintainer-authorized cleanup using the package-version API is a possible **owner-managed** expiry mechanism, subject to access, download-count restrictions, and explicit read-back; it is not guaranteed automatic expiry. Keep consumers on immutable manifest digests and release/delete only after checking named consumers. GitHub currently says Container Registry image storage and bandwidth are free, and warns that policy may change with at least one month's notice; this is a billing fact, not a retention limit. [GitHub Packages billing](https://docs.github.com/en/billing/concepts/product-billing/github-packages).

**Owner-approved safeguard:** review named consumers/digest pins every 3 days; retire an unconsumed candidate by day 7 only after verifying no consumer uses its digest. Never delete an active dependency; arrange migration or retain it under a named, time-bounded exception with an owner, reason, and next review date. This is manual policy, not a GHCR TTL. It reflects the owner-confirmed absence of private/external consumers and GitHub's documented manual version deletion, 30-day restoration window, and public-version download restriction. There is no hard maximum for a digest still in use. Recheck package-specific policy and download limits before any deletion; no GHCR package currently exists to test this workflow against. See [lifecycle evidence](issue-26-image-lifecycle.md#remote-registry-and-expiry-status).

**Can close:** the owner confirmed the consumer set and approved the 3-day review / day-7 unconsumed-candidate retirement policy; GitHub's documented manual deletion constraints and immutable-digest contract are recorded. This closes the policy definition without claiming a real package deletion test. Keep publication disabled until package-specific write access is configured and verified.
